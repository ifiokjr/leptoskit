# Hosted LeptosKit deployment service

The hosted pilot has one broker (`leptoskit_app`'s `leptoskit-cloud` binary), per-account journals, encrypted OpenTofu HTTP state, Stripe subscriptions, and one dedicated outbound worker per installation. The shared builder UI runs in browsers and native Wasm hosts. This extends the single-owner service without running customer builds or OpenTofu inside the shared broker.

## Product boundary

Account enrollment and DigitalOcean capacity provision are operator workflows. There is no public signup service, provider sub-account vending, automatic cloud-usage invoice reconciliation, model marketplace or Kubernetes executor. The control plan permits one installation; the team plan permits twenty. Both use operator-configured Stripe Price IDs. Prices such as USD 5 and USD 100/month must be created and reviewed in Stripe; cloud usage is separate. Do not advertise those prices as bundled, measured infrastructure costs.

Customer-owned compute can use a customer-hosted worker or a worker hosted by LeptosKit with that customer's credentials. LeptosKit-managed DigitalOcean compute uses an operator-owned installation and a separate credential/worker boundary per customer. A DigitalOcean project alone is not assumed to isolate API credentials. Never run unrelated customers under the same worker account, Docker daemon or provider token. Worker source checkouts are trusted within their dedicated installation.

DigitalOcean's [partner terms](https://www.digitalocean.com/legal/partner-network-terms-and-conditions) require application and program acceptance. Provisioning through the API does not itself establish resale rights. Agree on account ownership, quotas, tax and usage invoicing before enabling managed capacity. Actual provider execution, resale acceptance and usage settlement have not been tested by these repository tests.

## Operator setup

For a packaged Linux release and the pilot's cloud/payment acceptance sequence, follow [hosted pilot deployment and acceptance](hosted-pilot-acceptance.md). The steps below also support a manual build.

1. Package the public site, console client and documentation from the repository root with `cargo run -p leptoskit_app --features site --bin leptoskit-site -- --url https://deploy.example.com --release` (requires an installed `lk`; `--cli` selects another executable). Build the backend with `cargo build -p leptoskit_app --features server --bin leptoskit-cloud`. Copy the complete `crates/leptoskit_app/dist` artifact to the assets directory, including its `docs`, `console`, `pkg` and `rive` directories. Production binaries must be built for their deployment OS.
2. Supply `LEPTOSKIT_HOSTED_KEY` as a persistent random 32+ character key. It derives tenant API keys and state encryption. Back it up separately. The database records a key verifier and refuses a different key at startup. This V0 does not support online encryption-key rotation; changing the variable is not a rotation procedure.
3. Set `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, `STRIPE_CONTROL_PRICE` and `STRIPE_TEAM_PRICE`. Configure recurring prices and a billing portal with the intended upgrade/cancellation policy. The backend pins `2026-10-28.endive`. Register snapshot webhooks at `/api/v1/webhooks/stripe` for `checkout.session.completed` and `customer.subscription.created/updated/deleted`.
4. Create a Stripe customer, then enroll it with `leptoskit-cloud --data /srv/cloud account --id ACCOUNT --customer cus_...`. Store/deliver the printed account key through a private channel. The broker starts the account inactive; signed provider events grant access. The admin command can run while the broker serves.
5. Start `leptoskit-cloud --data /srv/cloud --url https://deploy.example.com serve --assets /srv/cloud-web --bind 127.0.0.1:4701` under a supervisor. `/` is the public landing page, `/console/` manages installations, and `/docs/` serves the actual book. The default book is `--assets/docs`; `--docs` can override it. Startup rejects an incomplete artifact. Put TLS/Cloudflare Tunnel and normal edge request limits in front. The app, fonts, Rive runtime, documentation and API share the same origin. Do not set up cross-origin bearer sharing.
6. For native builds, set `LEPTOSKIT_APP_ORIGIN` and the HTTP plugin origin allowlist to the real origin. Build/publish iOS and Android packages with the normal toolkit commands. Native Wasm compilation is validated; device behavior, signing, listings and payment-policy acceptance need separate validation.

For managed DigitalOcean capacity, first obtain an approved subscription, infrastructure quote and dedicated provider credentials. Configure the repository with `compute="digitalocean"`, an explicit budget, and the desired reviewed resources. Run `leptoskit-cloud ... managed --account ACCOUNT --project PROJECT`; it enables the managed installation and prints its pairing grant for the dedicated operator worker. An installation's ownership cannot be changed through the customer API. Initial DigitalOcean account/worker provisioning and cloud usage invoicing remain operator work.

## Requests and execution

The normal CLI endpoints retain their existing shape. Owner account keys resolve to one tenant's internally derived owner authority. Scoped keys carry an account prefix, then delegate through that tenant's existing scope checks. Worker keys are distinct, hashed, and limited to one fixed installation. Workers cannot read the customer's account or issue deployment keys.

The broker never accepts execution paths or shell commands. It hosts queue records; a worker claims only its project and invokes the existing fixed release commands against its local registered repository. The broker does not replay running records on its own restart. The agent persists a running marker before execution and a terminal result before acknowledgement. Ambiguous claims can leave an operation running; stop/revoke the old worker and reconcile it explicitly. A saved terminal result may be acknowledged repeatedly without executing again. Unknown running results are never inferred as successful.

The worker binds `TF_HTTP_ADDRESS`, lock/unlock addresses, username and password only into child command environments. Generated configuration selects an empty HTTP backend and contains no credentials. OpenTofu init must fail closed when an existing backend needs migration. State GET is allowed to the installation worker and the owning account; only the worker can write/lock. DELETE and unlocked writes are refused. Locks do not expire automatically. Matching lock IDs, serial monotonicity and lineage protect writes; twenty AES-256-GCM-SIV encrypted versions are retained per project, with account/project/version as authenticated data. The master key and state backups are both required for recovery.

The shared metadata store inherits the private SQLite directory, WAL, synchronous writes, busy timeout and approximate 1 GiB file bound. Each tenant journal has its own bound/retention. These limits are an early pilot capacity bound, not a promise of unlimited accounts or provider spend. Journal retention runs during worker traffic. Scale or replace storage before offering a public high-volume service.

## Billing behavior

Checkout uses a configured price, fixed return origin, a persisted reservation and an idempotency key. Retries reuse the same checkout; changing plan mid-checkout or retrying an expired/uncertain reservation requires operator reconciliation. Inspect Stripe before clearing its `checkout_*` fields; never clear an ambiguous reservation just to retry. Active subscriptions change through the billing portal.

Verify the raw body, timestamp tolerance and every candidate v1 signature before reading an event. Event IDs deduplicate accepted deliveries. Subscription notifications retrieve current Stripe state under a serialized refresh rather than applying old payload snapshots. Customer, single item, quantity and configured price must match. The broker refreshes known subscriptions on account/operation/worker requests after five minutes. Unknown/missed initial checkout events need operator replay from Stripe. Webhook/refresh failures do not grant access. Non-active/past-due/expired subscriptions block paid new work; existing resources are not destroyed or automatically stopped. Read access and state export remain available. Status, backup and compatible image rollback intents are permitted by the stored entitlement policy, although a billing provider outage can delay dispatch while refresh fails.

Payment verification tests use a local fake Stripe endpoint and signed payloads, not real charges. They cover forged/stale signatures, duplicate events, authoritative subscription status and duplicate checkout prevention. Follow [Stripe webhook guidance](https://docs.stripe.com/webhooks) and [Checkout API](https://docs.stripe.com/api/checkout/sessions/create) when preparing live-mode acceptance. No live payment acceptance is claimed.

## Backup, restore and reconciliation

Stop the broker for `leptoskit-cloud --data /srv/cloud backup --out /secure/cloud-backup`. Offline backup copies metadata/state and every account journal into a new private directory. Keep it off-site encrypted and retain the master key separately. The broker and online administration use shared maintenance locks; only one serving process can hold the server lock. Offline backup/schema rollback require exclusive maintenance access.

Restore into a new directory: `leptoskit-cloud --data /srv/cloud-restored restore --from /secure/cloud-backup`. It validates schemas, key verifier, integrity, foreign keys and latest state decryption before publishing the restored directory. It invalidates restored account keys, scoped tokens and worker pairings and interrupts restored running jobs. Stop old workers before switching data directories, rotate/deliver new account keys and re-pair workers, inspect retained state locks, and reconcile actual provider/release state before retrying any interrupted operation. The old data directory remains available.

Hosted migrations are paired, checksummed `001.up.sql`/`001.down.sql`. `rollback-schema --backup NEW_DIRECTORY --yes` is offline and deletes hosted account, state and billing metadata only after taking a complete backup. This first down migration is destructive. Starting again recreates an empty hosted schema; restore the backup to recover service identity and state. App-owned database reversals remain separate worker operations.

Revoke an uncertain worker from the app, stop it, then use `leptoskit-cloud ... interrupt --account ACCOUNT --operation ID` after inspecting remote infrastructure. That command requires the worker credential to be revoked. Preserve private logs and pending markers while investigating. Do not automatically erase running markers on startup.
