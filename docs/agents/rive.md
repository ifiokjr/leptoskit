# Native Rive integration

The public contract is in the [Rive guide](../src/guide/20-rive.md) and `leptoskit_rive/readme.md`. Native support is a CPU vector renderer, not full Rive feature parity. Native files cannot require text, images, fonts, layout, scripts, audio, or view models. Browser playback keeps using the app-supplied official runtime.

## Ownership and boundaries

- `leptoskit_rive_runtime` contains the pinned MIT C++ sources in a checksummed archive. It performs no build-time downloads. Keep its source revision, archive hash, and license together when updating it. The adapter compiles separately so Rust adapter edits do not rebuild the entire C++ library.
- `native::Player` owns one UI-thread runtime and a Rust raster context with a stable heap address. The context owner retains a raw allocation, so Rust moves and later borrows cannot re-tag a `Box` pointee behind C++'s retained pointer. Neither player nor context is `Send` or `Sync`. C++ destruction happens before the context is freed, including failed imports. Every pointer in a draw command is borrowed for that callback only. C++ exceptions stop at the C boundary; invalid draw data poisons the player.
- Native surfaces retain players by node identity and `(asset, artboard, scene)`. All changed input names/types are validated before applying a batch. Trigger sequences prevent unrelated renders from replaying triggers. The Wasm guest sends full content once; compact `rive_inputs` updates reuse only that node's installed scene. There is no global asset cache or cross-node reference lookup.
- Pixels never enter the guest or a render transaction. Swift, Kotlin, GTK, Win32, and ArkUI upload tightly packed premultiplied RGBA through synchronous native callbacks. Uploads own or copy their bytes before returning. Foreign callbacks must not reenter any function on the Rust app, including read-only queries.
- Encoded bytes are limited to 8 MiB, inputs to 64, and surface players to 16. Raster buffers have a 4,096-axis and 4,194,304-pixel per-player limit; a surface divides an 8,388,608-pixel budget among players and caps scale at 2. Paths, gradients, clip depth, and save depth are bounded at the raster boundary. These are not a sandbox or a bound on all decoded C++ object memory. Only trusted assets belong here.
- Deleted shadow slots retain their numeric IDs but clear owned props. Otherwise removed Rive files would remain alive in the arena. Backend transactions contain no asset bytes, so recording backends do not retain them either.

## Scheduling and image formats

Generated Apple hosts use CADisplayLink, Android uses Choreographer, GTK uses its frame clock, Windows sleeps on native messages with a capped frame deadline, and HarmonyOS uses DisplaySync. Stop subscriptions when scenes settle, pause, leave the viewport, become inactive, fail, or enter reduced motion. Commits and environment/scroll changes request one new callback. Reset elapsed time when restarting. A custom embedding owns the equivalent `tick_rive` or `tick_rive_with` loop.

AppKit reuses an NSBitmapImageRep, Windows reuses a top-down BGRA DIB, and Android reuses an ARGB_8888 Bitmap. Core Graphics and GDK receive owned upload copies. Android's raw ARGB_8888 buffer packing is ABGR as a native integer, so little-endian supported targets accept RGBA bytes; see the [Android Bitmap.Config contract](https://developer.android.com/reference/android/graphics/Bitmap.Config#ARGB_8888). Never premultiply these bytes again. Win32 swaps red/blue for GDI and flushes outstanding GDI operations before directly modifying or releasing the DIB, as required by the [CreateDIBSection synchronization contract](https://learn.microsoft.com/en-us/windows/win32/api/wingdi/nf-wingdi-createdibsection). Image property updates must not clear a paused Rive image.

HarmonyOS uses the API 12 PixelMap C API and Canvas. A JS PixelMap wrapper shares native ownership, never a pointer into the Rust raster buffer. Each upload creates an immutable PixelMap because [Canvas records a shared PixelMap for later rendering](https://github.com/openharmony/arkui_ace_engine/blob/master/frameworks/core/components_ng/pattern/canvas/canvas_paint_method.cpp); reusing and overwriting it could change an earlier queued frame. Canvas targets retain their latest frame for redraw after a paused resize, even when the bounded raster resolution stays unchanged. Device playback remains unverified by the existing SDK-only CI; validate it on the actual target. The host takes an application-provided reduced-motion preference through `AppStorage` key `leptoskit.rive.reduceMotion`.

## Verification

Run `devenv shell test:rive` for native pixels, retained surfaces, compact guest updates, the C ABI, browser policies, and actual offline browser playback. The vector fixture's source is `crates/leptoskit_rive/tests/fixtures/native/scene.rml`; regenerate it with the Rive CLI, verify, inspect, and render it before accepting a binary change. Compare its CLI screenshot with `target/rive-native/vectors-black.png`; tests separately assert premultiplied alpha values.

The platform widget suites exercise real AppKit, GTK, and Win32 uploads. SwiftPM controller tests and the UIKit controls app exercise generated Apple image ownership, paused property updates, decorative accessibility, and teardown. Run Android debug and release tests to cover both upload behavior and R8's JNI names. HarmonyOS needs both SDK ABI builds plus a device/emulator playback check. These boundaries complement each other; a successful SDK compile does not prove device rendering.

Run the normal workspace formatter, lints, tests, Wasm/WASI checks, strict docs build, and security gates before publishing. Do not report a frame-rate or latency claim from the tiny fixture alone. Measure realistic scenes and sizes in release mode, count successful changed frames, include native uploads, check idle/background CPU, and account for machine load and run-to-run variation.
